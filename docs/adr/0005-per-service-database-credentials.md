# ADR 0005 — One MongoDB account per service

- **Status:** Accepted and implemented
- **Date:** 2026-09-05

## Context

Each service already had its own logical database — `kapp_auth`, `kapp_user`, `kapp_semaphore`,
`kapp_schedule`, `kapp_map` — and there was no cross-database access anywhere in the code.

But MongoDB ran **without authentication**. Any process that could reach port 27017 inside the
compose network could read and write all five. The separation was a convention the code respected,
not a rule the engine imposed, and the anteproyecto's claim of *"servicios independientes, con base
de datos propia"* was true of the code and not of the system.

## Decision

`mongod` runs with `--auth` and a keyFile. Each service holds its own account with `readWrite` on
**exactly one** database, created **inside** that database.

## Rationale

**Creating the user inside the database it owns makes that database its own `authSource`.** The
connection string then names one database and nothing else — no reference to `admin` — so a leaked
credential opens one database and does not even hint at the others.

**It converts a convention into an invariant.** Nothing now stops a future service, or a bug, from
reading another service's data except the server refusing. `scripts/verify-db-isolation.sh` proves
it: each of the five accounts reaches its own database and is refused on the other four, 25 checks.

**It is what Atlas requires anyway.** A managed cluster has no unauthenticated mode, so this work
had to happen before the shared development cluster existed. Doing it locally first meant the
failure modes were found on a laptop.

## Alternatives considered

**One shared application account with `readWriteAnyDatabase`.** Simpler, one password. Rejected:
that is the state we were already in, with a password added — it makes no service unable to read any
other's data.

**Separate MongoDB instances per service.** Complete isolation, and genuinely what a production
deployment might do. Rejected as premature: five instances on a laptop, five backup procedures, and
five things to install on university hardware, to obtain a property the account model already gives.

## Consequences

- `.env` grows from one Mongo variable to twelve. It is generated by
  `scripts/generate-dev-secrets.sh` on each machine and never committed.
- A stale `.env` against a provisioned volume now fails loudly at the healthcheck rather than
  connecting to the wrong thing. That is the intended behaviour and the runbook says how to recover.
- **Atlas differs in one way that matters**: it stores all users in `admin`, so its connection
  strings carry no `authSource` pointing at the service's own database. The privilege scoping is the
  same — `readWrite` on one database — and `ATLAS-SETUP.md` spells it out, because getting it wrong
  produces "Authentication failed", which reads exactly like a wrong password.
